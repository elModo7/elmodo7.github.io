Project Overview

A document had finished downloading, but its unfinished chunk kept returning through the queue. The worker would start again, reach roughly the same point, exhaust its heap, and terminate. The broker would eventually redeliver the interrupted work.

Investigating that failure brought the platform's boundaries into focus. Streaming controls transfer buffers; conversion can still build a large in-memory model. Redelivery recovers interrupted work, but repeating a deterministic processing failure needs a different response.

The platform connects existing document repositories, relational metadata, cloud storage, and independently deployed services. Its purpose is to offer a consistent query and retrieval interface, then turn selected documents into downloadable exports without tying their processing to one HTTP request.

Platform Architecture

The source applications retain ownership of content access. Metadata is queried through database adapters, while binary retrieval follows the source applications' APIs, including SharePoint integration behind those boundaries where required.

Work messages carry identifiers and outcomes. Large binaries move through HTTP and object storage, keeping message size independent of document size. Query orchestration, export coordination, and conversion can therefore use different resource budgets.

Unified Queries & Cross-source Pagination

Spring GraphQL supplies the query entry point. Below it, search services choose sources, adapters interpret revisions and metadata, and SQL dialects handle database differences such as pagination syntax and null ordering. Filters use a known metadata catalog, typed operations, and parameterized values.

Related fields can multiply database calls. Batch mappings collect parent identifiers into bounded groups, while request-scoped reuse shares results across fields. Missing relationships are remembered too, avoiding repeated queries for the same absent parent.

A global page cannot be built by requesting the same page number from both repositories and concatenating the results. The service reads ordered candidates from each source, merges them, and advances each source's position only for records that enter the returned page.

The continuation cursor records the primary sort value and an identifier for deterministic tie-breaking. It is signed and bound to the query criteria. Cross-source ordering accepts one primary field, keeping the seek expressions and merge contract manageable. This federation happens in Java and SQL adapters.

Export pagination adds another layer because eligibility filtering can discard metadata candidates. Its cursor also tracks pending eligible identifiers. These are live repositories: a continuation position does not establish a snapshot across independently changing sources.

Sample Workflow: From Request to Download

  1. Accept and persist: the Export Service saves the request and preparation state, then returns an accepted response with a batch identifier.
  2. Select documents: a background preparation executor queries metadata and stores the ordered document list. Persisted preparation work can be rediscovered after a restart.
  3. Publish chunks: the combined list is split into bounded work units and sent to Service Bus.
  4. Process documents: workers use Spring Batch partitions, download originals, convert eligible formats, and upload results to Blob Storage.
  5. Record outcomes: correlated completion messages report stored results or explicit failures. Missing outcomes are checked before completion is published.
  6. Finalize: the Export Service assembles metadata and binaries into a temporary ZIP, uploads it, and exposes the archive for streaming download.

A partial export is distinguishable from a complete one. Every chunk being accounted for also differs from the final archive being available: compression and upload remain a separate finalization stage.

Recovery & Message Acknowledgement

Service Bus messages use a lock-based receive mode. Workers renew the lock while processing and acknowledge after the work finishes. If a process stops first, the broker can redeliver the chunk.

This is an at-least-once workflow. Workers check persisted completion evidence before repeating a finished chunk, and the Export Service recognizes previously completed chunks when consuming results. Publication, persistence, and acknowledgement still cross system boundaries, so recovery must account for interruptions between those steps.

Startup recovery handles persisted pending work and batches awaiting archive finalization. A conditional database update claims finalization across replicas, with a retry interval for abandoned claims. A lock inside one JVM would not coordinate overlapping replicas.

Structured download errors guide bounded retry policies, and a shared retry budget limits the time one chunk spends retrying documents. Invalid messages are explicitly dead-lettered; replay after exhausted delivery retries remains an operational responsibility.

Streaming, Conversion & Memory

Workers stream downloads into temporary files using a fixed-size copy buffer, enforce size limits during copying, and verify the received length when the source declares one. Interrupted transfers leave partial files that the helper removes.

Aspose.Words converts an explicit allowlist of supported Word-family formats, removes headers and footers, and produces PDFs. Other formats pass through as originals. Checking eligibility before invoking the parser avoids using a conversion exception as the normal format-rejection path.

Disk staging keeps the input and output bytes out of large application buffers, but the parser still constructs an in-memory document model. Layout complexity can dominate heap demand. A semaphore therefore serializes conversions within each process while other stages retain limited overlap.

Temporary storage has its own peak: originals and generated PDFs coexist during conversion, and archive assembly needs space for the finished ZIP. Cleanup surrounds response and processing lifecycles, including failed transfers. Uploaded originals retain their actual extensions.

Practical lesson: transfer buffers, parser memory, temporary disk, and final archive assembly need separate budgets. Increasing parallelism puts pressure on all of them.

Change Detection, Scaling & Deployment

Scheduled Kubernetes CronJobs query changes after a persisted watermark and publish bounded notifications to Service Bus topics. The watermark advances after successful publication. A partially published run can reappear, so deterministic message identifiers provide stable identities for repeated content.

Helm defines separate query, export, and worker deployments with CPU, memory, and ephemeral-storage budgets. Disk-backed temporary volumes support processing with a read-only root filesystem. KEDA uses Service Bus queue depth to adjust worker replicas within configured limits.

Queue messages have unequal costs. Replica decisions also need processing duration, conversion concurrency, downstream capacity, and schedulable node resources. Additional workers increase demand on source APIs, database connections, and storage.

JVM heap limits cover only part of container memory. Thread stacks, metaspace, native allocations, and I/O overhead also matter. A Java heap-space error, a container memory kill, and a probe-triggered restart require different evidence. More tolerant probes can accommodate a transient garbage-collection pause, but cannot resolve a parser that exhausts its heap.

Azure DevOps builds container images through Azure Container Registry tasks and deploys environment-specific Helm values to AKS. Build-qualified tags identify artifacts, while chart linting, manifest rendering, and rollout checks validate delivery.

Measuring the Complete Export

A Go runner submits requests, polls terminal state, downloads archives, checks ZIP integrity, and correlates HTTP timings with audit records. Acceptance latency, time to terminal state, and archive-transfer time describe different parts of the workflow.

Timing checks accompany delivered counts, explicit failures, and document-identity checks. A fast partial export is different from a complete result, and polling introduces uncertainty into observed completion time. Relationship resolvers can also add database work after the initial metadata lookup.

These measurements guide controlled experiments with page size, concurrency, and resource budgets. They do not establish sustained capacity without comparable workloads and recorded results.

What I Learned

The strongest decisions made ownership explicit: source applications own content access, adapters own metadata interpretation, workers own transformation, and export coordination owns the difference between accepted work, finished chunks, and a downloadable archive.

The recurring question was what evidence survives an interruption. A persisted request can be recovered, a recorded outcome can be recognized on redelivery, and a cursor can explain where traversal resumes. Those contracts make failures across independently deployed services reconstructable.
